# MICEPLANS 기능 명세서

## 1. 목적과 범위

MICEPLANS는 행사 운영 정보와 사내 지식을 한 제품에서 관리하는 웹 우선 업무 시스템이다. 남부 구성원은 행사, Program·Task·Subtask 일정, 알림, 개인 Todo, 행사 위키를 함께 관리하고, 고객은 자신에게 지정된 행사의 Program 일정과 과거 실적(행보)만 조회한다. AI는 정보를 읽고 초안을 제안할 수 있으나, 업무 데이터에 직접 변경을 실행하지 않는다.

이 문서는 2026-10-20 기준의 기능 범위와 수용 기준을 정리한 초안이다. 확정되지 않은 항목은 별도 표기하며, 구현 시 임의로 정책을 확정하지 않는다.

## 2. 사용자와 권한

### 2.1 역할 정의

| 역할 | 설명 |
| --- | --- |
| Super Admin | 모든 행사와 설정을 관리하는 내부 관리자 |
| PM | 행사를 총괄하는 담당자. 행사 멤버를 추가·삭제하고 행사 삭제를 실행한다 |
| AM | 행사 담당자. PM과 동일하게 행사 멤버를 추가·삭제한다 |
| 행사 멤버 | PM·AM이 행사에 추가한 내부 구성원. 해당 행사의 Program 이하 모든 항목을 편집한다. PM·AM은 행사 멤버를 겸한다 |
| Staff | 전체 행사를 조회하되 편집할 수 없는 내부 직원 |
| Client | 고객 포털의 별도 주체. 지정된 행사의 Program 일정만 조회한다 |

권한은 행사 단위로 부여되며, 행사 멤버가 되는 순간 그 행사의 Program 이하 모든 항목을 편집할 수 있다. 행사에는 항상 최소 한 명의 PM이 유지되어야 하고, 행사 삭제는 PM에게만 있다. 역할 변경과 담당자 변경은 현재 연결된 세션, 실시간 채널, 위키 편집 권한에 즉시 반영되어야 한다.

### 2.2 권한 매트릭스

| 기능 | PM | AM | 행사 멤버 | Staff | Client |
| --- | --- | --- | --- | --- | --- |
| 행사 조회 | 가능 | 가능 | 가능 | 전체 행사 | 지정된 행사의 Program만 |
| 행사 기본 정보 수정 | 가능 | 가능 | 가능 | 불가 | 불가 |
| 행사 삭제 | 가능 | 불가 | 불가 | 불가 | 불가 |
| 멤버 추가·삭제 | 가능 | 가능 | 불가 | 불가 | 불가 |
| Program 생성·수정·삭제 | 가능 | 가능 | 가능 | 불가 | 불가 |
| Task·Subtask 생성·수정·삭제 | 가능 | 가능 | 가능 | 불가 | 불가 |
| 담당자 지정 | 가능 | 가능 | 가능 | 불가 | 불가 |
| 개인 Todo | 본인만 | 본인만 | 본인만 | 본인만 | 해당 없음 |

Super Admin은 모든 행사의 생성·수정과 영구 삭제, 내보내기를 수행한다. PM·AM은 행사 멤버를 겸하므로 표의 멤버 권한을 모두 가진다.

행사 멤버의 위키·AI 권한은 2026-10-20 행사 플래너 명세에서 정해지지 않았다. 기존 결정은 아래와 같다.

| 기능 | PM·AM | Staff | Client |
| --- | --- | --- | --- |
| 행사 위키 조회 | 가능 | 가능(읽기 전용) | 불가 |
| 행사 위키 생성·수정·휴지통 삭제 | 가능 | 불가 | 불가 |
| AI 질의 | 가능 | 가능 | 불가 |
| AI 제안 승인 | 가능 | 불가 | 불가 |

Client는 내부 위키, 검색 결과, 인용문, 첨부 메타데이터, Socket.IO, Hocuspocus, AI 도구에 접근할 수 없다. Task, Subtask, 담당자, 내부 멤버 정보는 Client에게 노출하지 않는다.

### 2.3 데이터 구조

Event 아래에 Program, Task, Subtask가 한 계층으로 이어지며, 각 단계에 담당자를 지정하면 알림이 간다. 개인 Todo는 행사를 태그할 뿐 이 계층에 속하지 않고 본인에게만 보인다. 행사는 고객사에 속한다.

## 3. 공통 동작 규칙

### 3.1 데이터 보호와 감사

- 삭제 요청은 먼저 휴지통으로 이동하는 soft delete로 처리한다. 영구 삭제는 Super Admin만 실행할 수 있다.
- 업무 권한: 항목의 수정·삭제·담당자 지정은 만든 사람만 할 수 있다. 담당자가 지정된 항목의 완료 처리는 해당 담당자만 할 수 있고, 담당자가 없으면 만든 사람이 한다. 담당자는 행사 인력(PM·AM·Design·스태프) 중에서 지정한다. (현재 목업은 화면에서만 제한하며 서버·RLS 강제는 API 구현 시 추가한다.)
- 표 속성: 행사 상세의 진행상황·디자인 요청 표는 제목 옆 + 버튼으로 속성(텍스트·숫자·날짜·체크박스)을 추가하고, 속성 헤더를 눌러 이름을 바꾸거나 삭제할 수 있다. 속성 삭제 시 모든 행의 해당 값도 지워진다. 속성은 행사·표 단위로 저장한다. (현재 목업은 브라우저 localStorage에만 저장하며, 속성 변경 권한·감사 로그·서버 저장은 API 구현 시 정한다.)
- 삭제는 하위 항목까지 함께 적용된다. Program 삭제 시 그 아래 Task와 Subtask가 함께 삭제되고, Task 삭제 시 그 아래 Subtask가 함께 삭제되며, 행사 삭제 시 Program 이하 모든 항목이 삭제된다. 행사 삭제는 PM만 실행할 수 있다.
- 멤버를 삭제해도 그 사람의 개인 Todo는 영향을 받지 않는다.
- 담당자 지정·변경, Client 지정·공개 상태 변경, 영구 삭제, 내보내기, 권한 변경 및 AI 제안 반영은 `audit_log`에 남긴다.
- 모든 조회와 변경은 워크스페이스 및 요청 주체의 권한 범위에서 수행한다.
- Client 공개 데이터는 내부 기본 테이블이 아닌 공개 전용 모델을 통해 제공한다.

### 3.2 동시성 및 실시간 갱신

| 대상 | 규칙 | 사용자 경험 |
| --- | --- | --- |
| 제목, 설명 등 일반 텍스트 | 마지막 저장 우선 | 마지막 저장 결과를 화면에 반영 |
| 담당자, 마감일, 공개 상태 | 버전 검사 | 충돌 시 자동 덮어쓰지 않고 사용자에게 안내 |
| 위키 본문 | Yjs 병합 | 동시 편집, 커서, 접속자 표시 |
| 행사, Program·Task·Subtask, 알림 | 서버 푸시 후 조회 캐시 무효화 | 권한이 있는 사용자에게 최신 목록 반영 |

푸시 이벤트는 수신 권한을 확인한 사용자에게만 전달한다. 위키 접속자 위치는 줄 번호가 아니라 문단 또는 블록 단위로 표시한다.

## 4. 기능 명세

### F-01 인증과 워크스페이스 접근

내부 사용자는 Google Workspace OIDC와 PKCE로 로그인한다. 로그인 후에는 워크스페이스 역할과 행사 담당자 정보를 기준으로 화면, API, 실시간 연결의 접근 권한을 결정한다.

수용 기준:

- 내부 사용자는 인증되지 않은 상태에서 내부 기능에 접근할 수 없다.
- 권한이 회수되면 세션을 무효화하고 Socket.IO 방에서 제거하며, 열린 위키는 읽기 전용으로 전환하거나 연결을 종료한다.
- Client 인증 방식은 초대 기반 Magic Link 또는 고객사 SSO 중 아직 확정되지 않았다. Magic Link를 선택하면 보안 스캐너의 선열람을 막는 확인 단계 또는 6자리 코드가 필요하다.

### F-02 행사 관리

행사는 내부 운영의 최상위 업무 단위이며 고객사에 속한다. Staff는 전체 행사를 조회할 수 있으나 편집은 행사 멤버만 할 수 있다. 행사 멤버는 PM·AM이 추가하거나 삭제한다.

수용 기준:

- Staff는 모든 행사를 조회할 수 있지만 편집할 수 없다.
- 행사 멤버와 PM·AM은 자신이 속한 행사의 기본 정보, Program·Task·Subtask, 일정을 변경할 수 있다.
- PM·AM은 행사 멤버를 추가·삭제할 수 있고, 멤버 변경은 수정 권한과 실시간 연결 권한에 즉시 반영된다.
- 행사 생성 권한은 1단계 CRUD 구현 전에 결정한다. Staff가 생성하면 자동으로 PM이 되는 방식과 Super Admin만 생성하는 방식이 후보이다.

### F-03 Program·Task·Subtask 관리

행사 아래에 Program, Task, Subtask가 계층으로 구성된다. 행사 멤버는 Program 이하 모든 항목을 생성·조회·수정·삭제하고 각 단계에 담당자를 지정할 수 있으며, 담당자 지정 시 담당자에게 알림이 간다. 변경 사항은 권한을 가진 사용자의 화면에 실시간으로 반영된다.

수용 기준:

- Program·Task·Subtask의 생성·수정·삭제와 담당자 지정은 해당 행사 멤버와 PM·AM으로 제한된다. Staff는 조회만 한다.
- 삭제는 하위 항목까지 함께 적용된다. Program 삭제 시 하위 Task와 Subtask가 함께 삭제되고, Task 삭제 시 하위 Subtask가 함께 삭제된다.
- 담당자 및 마감일 변경은 버전 충돌을 검사한다.
- 개인 Todo는 Subtask와 별개의 데이터다. Todo에 행사를 태그해도 행사 쪽 화면에는 나타나지 않는다.
- 담당자가 행사 멤버가 아닌 경우 자기 항목의 상태 변경과 댓글을 허용할지는 미정이며, 내 할 일 보드 구현 전 결정한다.

### F-04 기업 화면

기업 사용자는 일곱 화면을 사용한다. 화면 구성과 세부 동작은 초안이므로 검토 후 확정한다.

| 화면 | 목적 | 주요 동작 | 편집 가능 대상 |
| --- | --- | --- | --- |
| 행사 대시보드 | 전체 행사를 한눈에 파악 | 진행 중·예정·종료 행사 목록, 행사별 진행 현황 표시 | 없음 (조회 전용) |
| 행사 상세 뷰 | 한 행사의 구조 관리 | Program > Task > Subtask 트리, 담당자·일정 표시, 멤버 목록 | 행사 멤버 |
| 연도별 보기 | 연 단위 행사 이력과 계획 파악 | 연도 선택 시 해당 연도 행사 목록 | 없음 (조회 전용) |
| 캘린더 뷰 | 날짜 중심으로 일정 확인 | 월·주 단위로 Program·Task 일정 표시, 행사/작업 일정 보기 전환 | 행사 멤버 |
| 할 일 (private) | 개인 업무 정리 | 행사를 태그해 나만의 Todo 뷰 생성 | 본인 |
| 고객사 보기 | 고객사별 행사 모아 보기 | 고객사 선택 시 해당 고객사의 행사 목록 | 없음 (조회 전용) |
| 알림 | 변경 사항 즉시 인지 | 알림 목록, 읽음 처리 | 본인 |

수용 기준:

- 조회 전용 화면(행사 대시보드, 연도별 보기, 고객사 보기)은 Staff도 사용할 수 있다.
- 행사 상세 뷰와 캘린더 뷰의 편집은 행사 멤버만 할 수 있다.
- 행사 상세의 할 일 탭은 스케줄 → 할일 → 하위 할일 계층으로 구성한다.
- 캘린더 뷰는 기본 행사 보기와 작업 일정 보기를 전환할 수 있다. 작업 일정 보기의 항목은 `[행사명] 제작물명`으로 표시하며, 디자인 제작물은 파랑·영상 제작물은 빨강 채움색으로 구분한다. 내 일정 탭에서는 로그인 사용자가 담당인 일정만 달력에 표시한다.
- 캘린더의 모든 보기에는 내 할 일이 함께 표시되며, 기간이 있는 할 일은 빗금 바, 마감일만 있는 할 일은 앞에 빗금 동그라미를 붙인 항목으로 구분한다.
- 캘린더 일정 상세 패널은 편집 모드에서 기간·장소·담당자·내 일정·설명·메모·Task·첨부 구성요소를 드래그해 순서를 바꾸고 삭제할 수 있다. 삭제한 구성요소는 다시 추가할 수 있으며, 배치는 브라우저에 저장한다.

### F-05 개인 Todo

개인 Todo는 행사 Subtask와 별개의 데이터로, 행사를 태그해 본인만의 할 일을 관리한다. Todo에 행사를 태그해도 행사 쪽 화면에는 나타나지 않는다. 멤버에서 삭제되어도 개인 Todo는 유지된다. 개인 Todo는 사용자의 컴퓨터에 먼저 저장하는 local-first 데이터이며, 초기 범위에서는 서버 동기화나 다중 기기 복구를 제공하지 않는다.

수용 기준:

- Todo의 생성·조회·수정·삭제는 본인 것만 가능하며 다른 사용자에게 노출되지 않는다.
- Client는 개인 Todo를 사용하지 않는다.
- Todo 변경은 네트워크 연결이나 서버 API 없이도 즉시 로컬에 반영된다. 브라우저 데이터 삭제·기기 교체 시 복구되지 않으며, 서버 동기화는 별도 요구가 확정될 때만 추가한다.

### F-06 알림 관리

내부 운영 알림을 생성·조회·변경하고, 행사와 Program·Task·Subtask의 실시간 변화를 사용자에게 전달한다. 알림 종류는 담당자 지정, 일정 변경, 마감 임박, 멤버 추가·삭제다.

| 알림 종류 | 발생 조건 | 수신 대상 |
| --- | --- | --- |
| 담당자 지정 | Program·Task·Subtask에 담당자가 추가될 때 | 지정된 담당자 |
| 일정 변경 | Program·Task·Subtask의 일정이 바뀔 때 | 해당 항목의 담당자 |
| 마감 임박 | 마감일이 가까워질 때 | 해당 항목의 담당자 |
| 멤버 추가·삭제 | PM·AM이 행사 멤버를 추가하거나 삭제할 때 | 추가·삭제된 당사자 |

수용 기준:

- 알림 갱신은 권한 필터를 통과한 Socket.IO 이벤트로 전달한다.
- Client는 내부 알림 채널에 연결하거나 알림을 조회할 수 없다.
- AI가 만든 알림은 즉시 발송하지 않고 제안으로 저장한다.
- 마감 임박 알림의 발송 시점과 일정 변경 알림의 수신 범위는 미확정(6절)이다.

### F-07 Client 포털

Client는 자신에게 지정된 행사만 조회할 수 있고, 행사 안에서는 Program 일정만 볼 수 있다.

| 기능 | 내용 | 노출 범위 |
| --- | --- | --- |
| 행사 일정 | 지정된 행사의 Program(예: 개막식) 일정을 날짜순으로 표시 | Program 이름과 일정 |
| 마이스 플랜즈 행보 | MICEPLANS가 수행한 과거 행사 실적을 소개 | 과거 실적 |

수용 기준:

- 지정되지 않은 행사는 목록에도 나타나지 않는다.
- Task, Subtask, 담당자, 내부 멤버 정보는 Client에게 노출하지 않는다.
- 위키, 검색, 태스크, 첨부 메타데이터, 실시간 방, 협업 연결, AI 질의는 모두 거부된다.
- 포털 앱은 포털용 계약과 공용 UI만 사용하며 내부 도메인·소켓 계약을 참조하지 않는다.

### F-08 Excel 일괄 가져오기

과거 행사 데이터를 Excel에서 가져와 행사 위키를 생성한다. 이 기능은 초기 사용 가능한 데모를 만들기 위한 2단계 범위다.

수용 기준:

- 가져오기 과정은 파일 선택, 컬럼 매핑, 미리보기, 검증, 실행의 다섯 단계로 구성한다.
- 파싱과 변환 작업은 비동기 작업으로 실행하며, 작업 입력에 워크스페이스와 실행 주체를 포함한다.
- 실패한 행과 이유를 사용자가 확인할 수 있어야 한다.
- 원본 파일과 변환 결과의 보존 정책은 구현 전에 확정한다.

### F-09 행사 위키와 협업 편집

행사 위키는 TipTap과 Yjs를 사용해 동시 편집한다. Yjs 원본을 기준으로 저장하고, Markdown은 검색 및 AI 읽기용 파생본으로 생성한다.

수용 기준:

- PM 또는 AM과 Super Admin은 행사 위키를 편집할 수 있다. Staff는 행사 위키에 읽기 전용으로 연결되며 커서와 접속자 표시는 볼 수 있다.
- Client는 협업 서버 연결을 포함해 위키의 어떠한 내용에도 접근할 수 없다.
- 문서별 열람 범위는 `전체 공개`, `행사 멤버`(기본값), `PM·AM만` 3단계로 설정한다. 범위 변경은 PM·AM과 Super Admin만 할 수 있으며 감사 로그 대상이다. Client는 어떤 범위에서도 볼 수 없다. 서버 강제는 `packages/db`의 `event_docs` RLS 정책(`can_view_doc`, `can_edit_event`)과 `packages/domain`의 `canViewDoc`·`canChangeDocVisibility`로 구현되어 실제 PostgreSQL 테스트(`packages/db/test`)로 검증한다. 현재 웹 화면은 선택 UI와 브라우저 저장만 제공하는 목업이며 API 연동은 NestJS API 단계에서 한다. 비멤버 내부 직원은 `staff`로 판정하므로 `행사 멤버` 범위에서는 보이지 않는다.
- 저장소는 update log, snapshot, `wiki_revision`을 분리한다. update log는 스냅샷 후 압축·정리하고, 명시적 버전 생성·제안 승인·발행·되돌리기에서만 `wiki_revision`을 만든다.
- 배포 중 협업 연결이 잠시 끊길 수 있으며 클라이언트는 재접속 후 동기화한다. Presence는 복구 대상이 아닌 일시 상태다.
- 공용 위키의 전 직원 편집 범위는 위키 에디터 단계 시작 전에 결정한다.

### F-10 파일, 지식 검색, 출처

업로드된 파일과 위키 파생본은 파싱, 청킹, 임베딩 과정을 거쳐 검색 대상이 된다. 검색은 권한 필터 후 lexical과 dense 결과를 병합하고, 결과와 AI 답변에는 출처를 제공한다.

수용 기준:

- 검색은 권한 필터, 행사·고객사·문서 유형·최신성 필터, FTS와 `pg_trgm`, dense 검색, 병합·재정렬 순서로 처리한다.
- 권한 밖의 문서는 제목, 요약, 인용문, 첨부 메타데이터를 포함해 검색 결과에 나타나지 않는다.
- 한국어 검색 품질은 골든 셋으로 측정한다. FTS와 `pg_trgm` 품질이 부족하면 별도 검색 엔진 및 BGE-M3 native sparse를 재검토한다.
- 파일 파싱, 청킹, 임베딩은 worker가 실행하고 검색 API와 worker가 동일한 지식 처리 코드를 사용한다.

### F-11 AI 질의와 제안

AI 에이전트는 권한 범위 내에서 행사 맥락, 일정, 태스크, 알림, 위키를 읽고 초안을 제안한다. 직접 쓰기 도구는 제공하지 않으며, 변경은 사람의 검토와 승인 후 서버 API가 수행한다.

| 단계 | 제공 기능 | 도구 |
| --- | --- | --- |
| 읽기 | 행사 맥락, 일정·태스크·알림 조회, 문서 검색·읽기 | `query_events`, `query_tasks`, `search_wiki`, `read_wiki_page` |
| 초안 생성 | 태스크·알림 초안, 체크리스트·회의록 요약, 일정·위키 수정 제안 | `propose_task_drafts`, `propose_notification`, `propose_wiki_edit` |
| 승인 후 실행 | 태스크 변경, 담당자 배정, 알림, 일정, Client 공개 | 사용자가 확인·승인한 뒤 서버 API가 실행 |

수용 기준:

- AI의 쓰기 성격 요청은 proposal만 생성하며, 승인 전 원본 데이터는 변경하지 않는다.
- 위키 제안 승인 시 서버는 에이전트 참여자로서 Yjs 트랜잭션을 수행하고 변경 출처를 남긴다.
- 승인된 반영은 모두 감사 로그에 기록한다.
- AI 응답은 SSE로 스트리밍하고, 호출별 프롬프트, 도구 호출, 토큰, 지연을 기록한다.
- GLM은 OpenAI 호환 어댑터 뒤에서 사용한다. 대표 시나리오 20~30개로 첫 2주 안에 도구 호출 품질을 평가하고, 모델 또는 프롬프트 변경 때 같은 골든 셋을 다시 실행한다.

### F-12 휴가·연차

내부 직원이 연차·대휴·반차·반반차를 신청하고 전 직원의 연차 사용 현황을 월별로 본다. 서버 저장소는 `leave_requests`, `weekend_work`이며 계약은 `packages/contracts`의 `leave`, 규칙은 `packages/domain`의 `leave`에 둔다.

| 형태 | 차감 일수 |
| --- | --- |
| 연차(`full`), 대휴(`comp`) | 1 |
| 오전·오후 반차(`am-half`, `pm-half`) | 0.5 |
| 오전·오후 반반차(`am-quarter`, `pm-quarter`) | 0.25 |

수용 기준:

- 신청과 취소는 본인 명의로만 한다. 취소는 soft delete다. 내부 직원은 전 직원의 사용 내역을 조회하고 Client는 조회할 수 없다.
- 주말에는 휴가를 신청할 수 없다. 반차·반반차는 하루만 신청한다. 같은 날 같은 형태의 중복 신청은 거부한다.
- 대휴를 제외한 휴가는 직원별 연간 연차 일수(`users.annual_leave_days`)를 넘길 수 없다. 대휴는 본인이 체크한 주말 근무 일수(근무 1일당 대휴 1일)를 넘길 수 없다. 두 한도는 DB 트리거로 강제한다.
- 주말 근무 체크(`weekend_work`)는 본인만 조회·변경한다. 현재 웹 목업은 이를 브라우저에만 저장하며, 서버 저장은 API 연동 단계에서 전환한다.
- 연차 현황의 `used`에는 대휴를 포함하지 않는다.

## 7. 구현 전 보완할 계약

다음 항목은 제품 동작에 영향을 주므로 각 기능 구현 전에 별도 계약으로 확정한다.

- 행사, Program, Task, Subtask, 알림의 필수 필드와 상태값. 현재 `packages/db/migrations/0002_core.sql`과 `packages/contracts`는 웹 목업에서 가져온 초안이다: 행사 상태 `진행중·성공·확인중·만료·제출·보류중`, 항목 상태 `할 일·진행 중·검토 대기·보류·취소·완료`, 제작 파트 `디자인·영상·3D`, 알림 종류 4종. 제작물·디자인 요청·표 속성·예산은 모델이 미확정이라 스키마에 없다.
- Program·Task·Subtask는 `event_items` 한 표에 `kind`와 `parent_id`로 저장하고 모든 행에 `event_id`를 유지한다. 삭제는 `soft_delete_event_item`·`soft_delete_event` 함수로 하며 하위 항목이 함께 삭제된다. 담당자는 행사 멤버만 지정할 수 있다.
- Client 포털은 `portal_events()`·`portal_programs()`만 사용한다. 지정된 행사의 `client_visible` Program에서 이름과 일정만 돌려주고, 내부 표에는 Client 정책이 없다.
- 클라이언트 행사 일정의 시간대, 취소 및 변경 표기
- 휴지통 보관 기간과 영구 삭제 절차
- Excel 템플릿, 매핑 규칙, 오류 처리, 원본 보관 정책
- AI 제안의 표시 형식, 승인·반려·재제안 흐름
- 골든 셋의 성공 기준과 모델 교체 기준
